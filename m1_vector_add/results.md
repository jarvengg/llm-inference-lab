# Vector Add 基线结果

测试时间：2026-09-03

## 环境

- GPU：NVIDIA GeForce RTX 5060 Laptop GPU，8 GB，`sm_120`
- 系统：Ubuntu 24.04 / WSL2
- Python 环境：`/home/wsy/triton-env`
- PyTorch：2.13.0+cu130
- Triton：3.7.1
- 数据类型：FP32
- `BLOCK_SIZE`：256

## 正确性

FP16 和 FP32 均通过以下尺寸：

```text
0, 1, 127, 256, 257, 1024, 2049, 65536, 1000003
```

所有测试的最大绝对误差均为 0。尺寸 257、2049 和 1,000,003 验证了非整块输入的 mask 逻辑。

## Benchmark 方法

- PyTorch 与 Triton 分别预分配 output，计时区间不包含显存分配。
- 使用 `triton.testing.do_bench` 预热并重复执行。
- 表中延迟采用 50% 分位数，即 median。
- 有效带宽按 `3 × n_elements × sizeof(float32) / time` 计算：读取两个输入，写入一个输出。

## 原始结果

| elements | PyTorch ms | Triton ms | PyTorch GB/s | Triton GB/s |
|---:|---:|---:|---:|---:|
| 4,096 | 0.006016 | 0.006048 | 8.17 | 8.13 |
| 16,384 | 0.006096 | 0.006128 | 32.25 | 32.08 |
| 65,536 | 0.008064 | 0.008064 | 97.52 | 97.52 |
| 262,144 | 0.012320 | 0.016352 | 255.34 | 192.38 |
| 1,048,576 | 0.046144 | 0.044704 | 272.69 | 281.47 |
| 4,194,304 | 0.153184 | 0.153664 | 328.57 | 327.54 |
| 16,777,216 | 0.587680 | 0.587984 | 342.58 | 342.40 |

## 当前可以得出的结论

1. 小尺寸下两者都约为 6 微秒，固定启动开销占主导，所以有效带宽很低。
2. 输入增大后，有效带宽逐渐上升，说明固定开销被摊薄。
3. 最大尺寸下 PyTorch 为 342.58 GB/s、Triton 为 342.40 GB/s，差异约 0.05%，可以视为同一水平。
4. 这符合 Vector Add 的访存受限特征：每个元素只有一次加法，却需要两次读取和一次写入。
5. 262,144 元素处 Triton 明显落后，但单次基线不能说明原因。需要复测不同 `BLOCK_SIZE` 并观察重复运行稳定性后才能判断。

## 现在不能得出的结论

- 不能说 Triton 在所有尺寸都比 PyTorch 快。
- 不能把本次有效带宽直接当作 GPU 标称显存带宽。
- 不能根据 262,144 这一个异常点立即开始优化 Kernel。
- 未固定笔记本功耗、温度和后台负载，因此这组数据是学习基线，不是正式硬件评测。

## 下一实验

保持 Kernel 逻辑不变，只比较 `BLOCK_SIZE = 128 / 256 / 512 / 1024`。目标是理解 block 大小怎样影响 program 数量与性能，然后再判断是否需要 `@triton.autotune`。

## BLOCK_SIZE 受控实验

测试时间：2026-09-03

实验固定 `num_warps=4`，只改变 `BLOCK_SIZE`。四种配置均通过 1,000,003 元素的非整块正确性测试。

| elements | block size | programs | Triton ms | Triton GB/s |
|---:|---:|---:|---:|---:|
| 262,144 | 128 | 2,048 | 0.015616 | 201.44 |
| 262,144 | 256 | 1,024 | 0.016000 | 196.61 |
| 262,144 | 512 | 512 | 0.014208 | 221.41 |
| 262,144 | 1024 | 256 | 0.012224 | 257.34 |
| 1,048,576 | 128 | 8,192 | 0.048768 | 258.02 |
| 1,048,576 | 256 | 4,096 | 0.048704 | 258.35 |
| 1,048,576 | 512 | 2,048 | 0.046784 | 268.96 |
| 1,048,576 | 1024 | 1,024 | 0.045024 | 279.47 |
| 4,194,304 | 128 | 32,768 | 0.155488 | 323.70 |
| 4,194,304 | 256 | 16,384 | 0.153120 | 328.71 |
| 4,194,304 | 512 | 8,192 | 0.153824 | 327.20 |
| 4,194,304 | 1024 | 4,096 | 0.153696 | 327.48 |
| 16,777,216 | 128 | 131,072 | 0.601552 | 334.68 |
| 16,777,216 | 256 | 65,536 | 0.592736 | 339.66 |
| 16,777,216 | 512 | 32,768 | 0.589664 | 341.43 |
| 16,777,216 | 1024 | 16,384 | 0.589632 | 341.44 |

观察：

- 262,144 元素时，1024 相比 128 将 program 数量减少 8 倍，带宽从 201.44 提升到 257.34 GB/s。
- 1,048,576 元素时，1024 仍然最好，但相对优势缩小。
- 4,194,304 元素及以上，各配置已经接近同一带宽平台；细小差异不能解释为稳定优劣。
- 16,777,216 元素时，512 与 1024 几乎完全相同，说明此时瓶颈主要是显存带宽，而不是 program 数量。
